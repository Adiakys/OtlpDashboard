# Demo module

Mock-telemetry layer for the static GitHub Pages build of the SPA. Loaded
**only** when `import.meta.env.VITE_DEMO_MODE === 'true'` at build time —
the import lives behind a literal compare in `plugins/services.ts`, so
the entire subtree (generators, fixtures, routes, fetcher, storage) is
dead-code-eliminated in production bundles.

## How it plugs in

`HttpClientService` already accepts an injected fetcher
(`web/app/services/HttpClientService.ts`). The plugin builds either:

- **prod**: `$fetch.create({ onResponseError })` — the real network
- **demo**: `createDemoFetcher(deps, { onResponseError })` from `./fetcher.ts`

Same downstream feature services (`MetricsService`, `LogsService`, …),
same auth flow (login page intact, 401 redirects intact). The demo
fetcher inspects the `Authorization` header itself; any non-empty bearer
token authenticates, so any password the user types through the login
form gets accepted.

## Layout

```
demo/
├── index.ts          # createDemoBootstrap — only public surface
├── fetcher.ts        # `typeof $fetch`-compatible function
├── routes.ts         # Path → handler dispatch
├── storage/
│   ├── StorageService.ts
│   ├── InMemoryStorage.ts        # default
│   └── LocalStorageStorage.ts    # swap-ready, unused
├── state/
│   ├── DashboardStore.ts
│   └── WidgetDefinitionStore.ts
├── data/
│   ├── _bundled.json   # GENERATED — `pnpm sync-demo-fixtures`
│   ├── bundle.ts       # typed wrapper
│   ├── services.ts     # ['sample-server', 'sample-client', 'postgresql', 'redis']
│   ├── instruments.ts  # the metric catalog every demo widget needs
│   ├── dashboards.ts   # seed dashboards from the bundle
│   └── libraries.ts    # widget libraries from the bundle
└── generators/
    ├── prng.ts         # mulberry32 + helpers (gaussian, range, pick…)
    ├── metrics.ts      # random-walk per instrument
    ├── traces.ts       # lognormal durations, op-name catalog
    └── logs.ts         # severity distribution, ~5% trace correlation
```

## Updating the bundled fixtures

`_bundled.json` is regenerated by:

```
pnpm sync-demo-fixtures
```

That script (`web/scripts/sync-demo-fixtures.mjs`) walks
`demo/packs/*/pack.json` at the repo root and emits a deterministic JSON
containing each pack's libraries (and their widgets) plus its dashboards.
Re-run after you add or edit a demo pack asset.

`pnpm generate:demo` runs sync first, so CI is always current.

## Switching to localStorage persistence

Mutations (create / edit / delete dashboard) live behind
`StorageService` so they can survive page reloads with one line:

```diff
- const storage = new InMemoryStorage()
+ const storage = new LocalStorageStorage('oteldash-demo:')
```

…in `index.ts`. Default is in-memory because it keeps the demo a
deterministic sandbox — every visitor sees the same seed.

## Determinism

A seeded mulberry32 PRNG drives every `Math.random` substitute. Seeds
are derived from the request signature (path + key query params), so
the same widget asking the same question across refreshes sees the
same numbers. The metric instruments' `resourceHash` is the literal
string `demo-<service>` — stable, no hashing.
